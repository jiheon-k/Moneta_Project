# Moneta 구조 검토와 단계별 개발 지침

작성일: 2026-10-26

## 1. 문서의 목적과 사용 방법

현재 코드의 장점, 문제점, 개선 방향을 기록하고 이후 학습·개발의 기준으로 사용한다.
사용자가 구조 검토 후 이 문서를 지침으로 저장하고, 추천 순서에 따라 천천히 진행하도록 요청했다.

- 기본 계층 구조와 기능별 패키지는 유지한다.
- 다음 목표는 지출 등록부터 거래 조회·잔액 확인까지 이어지는 실제 사용 흐름이다.
- 한 번에 하나의 작은 구현 단위만 진행한다. 전체 로드맵을 일괄 구현하지 않는다.
- 2026-11-18 사용자 지시: 현재 테스트 오류 수정·확인 이후에는 기능 개발이 완전히 끝날 때까지 테스트를 추가·수정·실행하지 않는다. 중간 단계마다 테스트를 정리하지 않고, 기능 개발 완료 후 모아서 진행하며 미검증 상태를 검증 완료로 표시하지 않는다.
- 백엔드는 설명 → 사용자의 구현 → 코드 검토 순서로 진행한다. 명시적으로 작업을 맡기면 해당 범위만 직접 수정한다.
- 새로운 단계에 들어갈 때 현재 코드와 Git 변경 상태를 다시 확인한다.
- 아래의 추천 정책은 아직 구현됐다는 뜻이 아니다. 미결정 사항은 해당 단계에서 하나씩 정한다.
- 최신 사용자 지시와 실제 코드가 우선이다. 완료 상태는 실제 구현·검증 근거가 있을 때만 갱신한다.

## 2. 2026-10-26 검토 당시 상태 (이후 변경은 7절 참고)

Java 21, Spring Boot 4.1.1, Gradle Wrapper 9.7.1, Spring Data JPA, MySQL을 사용하는 백엔드와 React·TypeScript 프런트엔드가 있다.
버전은 검토 당시 설정 기준이며 이후 작업에서는 실제 파일을 우선한다.

| 영역 | 구현 상태 |
|---|---|
| 인증 | 회원가입, 세션 로그인, 현재 사용자 조회, 로그아웃, CSRF 처리 |
| 계좌 | 생성, 단건 조회와 잔액 계산, 부분 수정, 삭제, 소유자 검사 |
| 카테고리 | 공통·본인 목록, 개인 항목 생성·수정·삭제, 소유자 검사 |
| 거래 | Entity, Repository, 계좌별 기간·유형 조회와 DTO 변환 |
| 거래 등록 | 요청 DTO가 비어 있고 생성 Controller·Service는 없음 |
| 계좌 목록 | API 없음. 화면에서 ID를 직접 입력해 단건 조회 |
| 화면 | 인증, 계좌·카테고리 관리, 거래 조회. 거래 등록은 없음 |

- 테스트 통과는 아직 구현하지 않은 거래 생성이나 실제 금액 계산의 정확성까지 보장하지 않는다.

## 3. 유지할 장점

1. **기능별 패키지와 계층 분리**: `account`, `category`, `transaction`, `auth`를 구분하고 Controller·Service·Repository의 책임을 나눴다. 현재 규모에서 불필요한 공통 상속이나 Service 인터페이스를 추가하지 않는다.
2. **소유자 기준 접근**: 세션의 사용자 ID와 `findByIdAndUser_Id()`를 사용한다. 클라이언트가 주장하는 사용자 ID를 소유권의 근거로 사용하지 않는다.
3. **금액과 날짜 타입**: 원화 정수는 `Long`, 거래 날짜는 `LocalDate`로 표현한다.
4. **이체 모델**: 출금 계좌와 입금 계좌가 연결된 한 거래로 표현하고, 이체를 수입·지출 통계와 구분한다.
5. **거래 기반 잔액 계산**: 초기 잔액에 유입을 더하고 유출을 빼는 구조를 유지한다. 별도 잔액 저장은 실제 성능·업무 요구가 생기면 검토한다.
6. **DTO 사용**: Entity를 그대로 응답하지 않는다. 계좌 부분 수정에서 생략·명시적 null·공백을 구분한다.
7. **세션 인증**: 비밀번호 해시, 세션 ID 교체, 인증 정보 저장, CSRF 갱신, 로그아웃, 인증 객체의 해시 제거를 유지한다.
8. **실패 처리**: 공통 오류 응답과 화면의 중복 제출 방지·세션 만료·연결 실패 처리를 유지한다.

## 4. 우선 해결할 문제와 추천 방향

### 4.1 거래 등록 흐름 미완성

`TransactionRequest`는 비어 있고 거래 생성 API가 없다. 인증과 관리 기능을 더 확장하기보다 지출 등록을 기존 조회·잔액 계산에 연결한다.

목표 흐름:

```text
로그인 → 본인 계좌 선택 → 지출 입력 → 저장 → 거래 목록 확인 → 잔액 감소 확인
```

### 4.2 거래 소유자 중복

현재 `Transaction.user`와 `Transaction.account.user`가 함께 존재한다. 외래키는 대상의 존재를 확인하지만 두 사용자의 일치까지 보장하지 않는다.

- 결정: 2026-10-26 사용자가 계좌 소유자를 거래 소유권의 기준으로 선택했다. `Transaction.account.user`를 기준으로 판단하고 중복 `Transaction.user`를 단계적으로 제거한다.
- 이체의 도착 계좌도 출금 계좌와 같은 사용자 소유인지 서버가 검증한다.
- 요청의 사용자 ID를 신뢰하지 않는다. 거래 생성 전 로그인 사용자 ID와 계좌 ID로 본인 계좌를 조회한다.
- 현재 거래 생성 API가 없으므로 확인된 정보 유출로 단정하지 않는다.
- 필드 제거 전 `TransactionUnit`, `AccountService`, 테스트, 설계 문서, DB 이전 SQL의 의존성을 확인한다. Entity만 수정하거나 실제 DB 컬럼을 임의로 삭제하지 않는다.

### 4.3 거래 생성 규칙 부재

다음 규칙을 거래 등록 구현 단계에서 연결한다.

| 위치 | 책임 |
|---|---|
| 요청 DTO | 금액 필수·양수·상한, 날짜 필수, 메모 길이 등 입력 검증 |
| Service | 계좌·카테고리 존재 여부와 소유권, 기능 처리 순서 |
| Entity 생성·변경 메서드 | 거래 유형에 맞는 필드 조합과 올바른 상태 유지 |

기본 거래 규칙:

- 금액은 양수이며 원 단위 정수다.
- 수입·지출에는 거래 계좌가 필요하고 이체 도착 계좌는 없다.
- 이체에는 서로 다른 출금·입금 계좌가 필요하고 두 계좌는 같은 사용자 소유다.
- 카테고리를 지정하면 공통 또는 본인 소유여야 한다.
- 카테고리 필수 여부, 금액 상한, 메모 길이, 미래 날짜 허용 여부는 해당 구현 전에 정한다.

`nullable = false`만으로 양수나 계좌 조합 규칙을 보장할 수 없다. 모든 setter를 한꺼번에 재설계하기보다 거래 생성 메서드부터 작은 단위로 개선한다.

### 4.4 거래가 연결된 항목의 삭제

계좌·카테고리는 조회 후 바로 삭제한다. 참조하는 거래가 있으면 DB 제약으로 거절될 수 있으며, 현재 예외 처리 구조에서는 일반 500 응답이 예상된다. 실제 MySQL에서 재현한 결과는 아니다.

추천 초기 정책:

- 거래가 없으면 삭제 허용.
- 거래가 연결되어 있으면 삭제 거절, 409와 이해 가능한 설명 반환.
- 이체의 출금·입금 양쪽 계좌 참조를 모두 확인.
- 사전 검사와 별도로 동시 요청에 따른 DB 제약 실패도 처리.
- 모든 DB 무결성 오류를 무조건 같은 409로 바꾸지 않는다.
- 과거 거래는 보존하고, 보관·비활성화 기능은 필요해질 때 검토.

### 4.5 초기 잔액과 날짜 기준

현재 초기 잔액은 거래 존재 여부와 무관하게 수정할 수 있고, 기준일 필드가 없다. 거래 합계는 미래 날짜도 포함한 전체 기록을 대상으로 한다.

구현 전 결정할 사항:

- 초기 잔액의 기준일과 그 이전 거래 허용 여부.
- 거래 등록 후 초기 잔액 수정 제한 또는 별도 정정 방식.
- 미래 거래의 허용 여부와 현재 잔액 반영 기준.
- 초기 잔액의 음수 허용 여부. 부채 표현 정책에 따라 결정하며 무조건 입력 오류로 보지 않는다.

이 항목을 이유로 잔액 정정·예약 거래 같은 기능을 선제적으로 모두 구현하지 않는다.

### 4.6 가계부 계산·접근 제어 테스트 부족

`TransactionRepositoryQueryTests`는 쿼리 해석을 검사하며 실제 데이터를 저장해 합계 결과를 비교하지 않는다. 기존 Service 테스트도 주로 모의 객체를 통한 DTO 변환 검사다.

우선 추가할 검증:

- 거래가 없을 때 잔액 = 초기 잔액.
- 수입·지출이 정확히 잔액에 반영됨.
- 이체 시 양쪽 계좌의 변화와 전체 잔액 합계 보존.
- 시작일 포함·종료일 제외, 같은 날짜에서 ID 기준 정렬.
- 사용자 A의 세션으로 사용자 B의 항목 조회·수정·삭제 차단.
- 공통 카테고리 수정·삭제 차단.
- 거래가 연결된 항목의 삭제 실패 응답.

개발 MySQL에 임의 테스트 데이터를 넣거나 테이블을 초기화하지 않는다. MySQL 고유 동작 검증은 격리된 테스트 환경에서 수행한다.

## 5. 기능 구현과 함께 보완할 사항

| 항목 | 현재 상태와 개선 방향 |
|---|---|
| 계좌 목록 | `GET /accounts`로 본인 계좌 선택 가능하게 한다. 목록의 잔액 계산에서 단건 쿼리를 무조건 반복하지 않는다. |
| 카테고리 응답 | `editable` 또는 `common` 등으로 화면에서 수정 가능 여부를 판단하게 한다. 서버 권한 검사는 유지한다. |
| 트랜잭션 경계 | 계좌 조회와 유입·유출 합계를 하나의 작업으로 검토한다. `readOnly` 자체가 일관된 시점을 보장하는 것은 아니며 DB 격리 수준도 확인한다. |
| 어노테이션 일관성 | Jakarta와 Spring의 `Transactional` 혼용은 즉시 오류가 아니다. 읽기 전용 설정이 필요하면 Spring 쪽 통일을 검토한다. |
| 연관 객체 조회 | `ManyToOne`의 기본 즉시 조회로 추가 쿼리가 늘 수 있다. 실제 SQL을 확인한 뒤 조회 전략과 DTO 변환 시점을 함께 개선한다. |
| 목록 크기 | 거래 목록의 페이지 단위 조회를 추가하고, 실제 조건·실행 계획을 기준으로 인덱스를 검토한다. |
| API 이름 | `account_name`, `account_type`, `tList` 등을 명확하고 일관된 이름으로 정리하되 화면과 함께 변경한다. |
| HTTP 응답 | 생성 201, 본문 없는 삭제 204 등의 규칙을 정한다. 기존 200을 모두 오류로 취급하지 않는다. |
| 금액 범위 | Java `Long`과 JavaScript `number`의 정수 표현 범위가 다르므로 현실적인 상한을 정해 양쪽에 적용한다. |
| 화면 구조 | 기능이 커질 때 계좌·카테고리·거래 영역을 분리한다. 현재 전체 상태 관리 라이브러리를 새로 도입할 필요는 없다. |

## 6. 설정·문서·유지보수

- `application.properties`는 Git 추적 대상이고 DB 주소·사용자명이 직접 설정되어 있다. 검토 시 비밀번호는 빈 값이었다. 환경변수 또는 Git에서 제외한 로컬 설정으로 분리한다.
- `ddl-auto=update`는 로컬 학습과 중요한 데이터가 있는 환경을 구분해서 사용한다. 수동 SQL을 포함한 DB 변경 이력·적용 순서를 관리한다.
- 기존 `UserService.createUser()`는 인증 필수 필드를 채우지 않는 연습 코드다. 현재 호출 경로는 없지만 재사용 시 실패할 수 있으므로 정리한다.
- 미사용 빈 타입 `AuthnticationPrincipal`, `GenerationTpye`는 참조 확인 후 정리한다.
- `Moneta_DB_Design.md`, `docs/auth.md`에는 현재 인증·소유자 검사·거래 사용자 필드와 어긋나는 설명이 있다. 관련 단계에서 갱신한다.
- 예외 클래스 이름만 기록하는 로그를 보완한다. 오류 위치와 원인을 추적하되 비밀번호·토큰·요청 본문을 무분별하게 기록하지 않는다.
- 이름·나이가 실제 가계부에 필요한지 검토한다. 가입 DTO와 Entity의 이름·나이 허용 범위 차이도 정리한다.
- 세션 인증과 현재 계층 구조를 유지한다. 현재 문제 해결을 위해 인증 기술 교체나 대규모 구조 변경을 추진하지 않는다.

| 2 | 본인 계좌 목록 조회 | ID를 기억하지 않고 계좌 선택 가능 | 완료 |
| 3 | 지출 등록 | 입력 검증·소유권 검증 후 정상 저장 | 완료 |
| 4 | 거래 내역·잔액 검증 | 실제 저장한 지출이 목록·잔액에 정확히 반영 | H2 통합 테스트 완료. 기존 MySQL은 미검증 |
| 5 | 지출 단건 조회·수정·삭제 | 기존 기록과 잔액이 일관되게 변경 | API 구현 및 H2 검증 완료 |

이 순서는 기본 안내다. 해당 기능에 필요한 오류 처리·테스트·문서 갱신은 각 단계에 함께 포함한다. 모든 정리 작업이 끝나야 지출 등록을 시작할 수 있는 것은 아니다.

### 2026-11-18 기본 사용 흐름 구현

사용자가 기본 기능 전체 구현과 각 Controller·Service·Repository의 역할 주석을 요청했다.
추가로 실험용 DB와 프런트엔드도 요청했다. 이에 따라 아래 범위만 구현했다.

- `GET /accounts`: 본인 계좌 선택용 목록. 목록마다 잔액 계산 쿼리를 반복하지 않는다.
- `POST /expenses`: 본인 계좌·공통 또는 본인 카테고리 확인 후 지출 저장, 201과 ID 반환.
- 금액 1~1조 원 정수, 오늘까지 날짜, 메모 255자, 카테고리 생략 허용.
- 요청의 소수 금액을 정수로 잘라 저장하지 않고 400으로 거절.
- 거래 등록 후 초기 잔액 변경과 거래가 연결된 계좌·카테고리 삭제는 409로 거절.
- 초기 잔액은 기록할 거래들 직전의 금액으로 입력한다. 별도 기준일 필드는 없으며 과거 날짜 입력은 허용한다.
- React 화면의 계좌 목록 선택, 지출 입력, 저장 후 해당 날짜의 거래·잔액 갱신 연결.
- 공통 카테고리 응답에 `common`을 추가하고 화면의 수정·삭제 버튼 비활성화.
- 각 Controller·Service·Repository(인증 포함)에 역할 주석 추가.
- `demo` 프로필: 기존 MySQL과 별개의 H2 파일 DB, 예제 계정·계좌·카테고리·지출을 최초 1회 생성.
- 실험 화면 `npm run dev:demo`: localhost:5174, 백엔드 8081. 실행 방법과 계정은 루트 README 참고.

기능 구현 중 테스트를 수정·실행하지 않고, 전체 기본 기능 구현 후 최종 검증 단계에서 모아서 진행했다.
지출 수정·삭제, 수입·이체 등록, 통계는 이번 범위에 포함하지 않았다.

### 다음 대화의 시작점

실험용 화면에서 직접 지출을 기록하며 현재 코드의 요청 흐름을 살펴볼 수 있다.
백엔드의 다음 구현 순서는 수입·이체 연결이며, 유형별 규칙을 한 가지씩 정한다.
이후에도 중간 구현 단계마다 테스트를 건드리지 않고 기능 완료 후 검증한다.

기존 MySQL은 이번에 접속하거나 변경하지 않았다. 이전 사용자가 공유한 결과에서는
`transaction.user_id`와 해당 외래키 제거가 확인됐고, 과거 `from_account_id`·`to_account_id`는 남아 있었다.
기존 DB를 사용할 때는 실제 스키마와 이전 제약조건 상태를 별도로 확인해야 한다.
DTO의 `userId`는 유지하며 계좌 소유자를 기준으로 채운다.

### 2026-11-28 지출 단건 API 구현

- `GET /expenses/{id}`는 본인 지출 상세를 반환한다.
- `PUT /expenses/{id}`는 등록과 같은 형식으로 기존 지출 전체를 수정한다. 본인 계좌 사이 이동이 가능하고 생략한 선택 필드는 비워진다.
- `DELETE /expenses/{id}`는 거래를 삭제하고 204를 반환한다. 계좌 잔액은 변경된 거래 내역으로 계산한다.
- 세 API 모두 본인 지출만 대상으로 삼는다. 수정·삭제는 트랜잭션 안에서 같은 지출에 대한 변경 요청을 순서대로 처리한다.
- `./gradlew test --offline --console=plain --no-daemon`에서 74개 통과. 계좌 이동·삭제 후 잔액, 변경된 거래 내역, 잘못된 입력과 타인 접근 차단을 H2에서 확인했다. 실제 MySQL과 동시 변경 시나리오는 검증하지 않았다.
